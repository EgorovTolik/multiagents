# Анализ задачи из JIRA — глобальный навигатор

Этот навык описывает общий принцип работы с задачами, созданными через Jira. Его цель: по описанию задачи определить, какие продукты (проекты) будут затронуты, собрать артефакт для передачи цепочке работ и записать ответы пользователя в локальную базу знаний.

## Общие принципы

1. **Прочитать задачу целиком.** Сумму, описание, комментарии, вложения (скриншоты), подзадачи, чеклист — всё может содержать подсказки о продуктах.
2. **Определить продукты.** Продукт = программный продукт с собственным репозиторием кода. Названия продуктов могут встречаться как явно ("Мобильное приложение"), так и неявно (URL-адреса, домены, имена сервисов в описании).
3. **Собрать артефакт.** Записать анализ в `shared/jira-analysis/<task-key>/analysis.json` + краткое резюме в `shared/jira-analysis/<task-key>/summary.md`. Это будет входом для агентов-исполнителей (планировщик, кодер, ревьюер).
4. **Запомнить ответы пользователя.** Если пользователь уточнил что-то о продукте/репозитории — запиши в `shared/jira-analysis/known_answers.json` (ключ-значение), чтобы не спрашивать повторно.

## Карта продуктов

Перед началом работы прочитай этот блок кода из своего контекста — это карта всех известных продуктов:

```json
{
  "ANDROIDSERVICE": {
    "name": "AndroidService",
    "slug": "androidservice",
    "description": "",
    "repo_url": "",
    "products": []
  },

  "_templates_": [
    "Заполни ссылку на репозиторий в поле repo_url. products — список slug-ов продуктов, которые входят в этот проект.",
    "Пример: \"Мобильное приложение\" → slug \"mobile-app\", \"Веб-админ панель\" → slug \"admin-panel\""
  ]
}
```

Если продукт найден в задаче, но отсутствует на карте — уточни у пользователя (см. ниже).

## Сценарии работы

В зависимости от типа задачи примени соответствующий блок сценария из своего контекста:

| Ключевые слова в заголовке | Сценарий |
|---|---|
| "Исследовать", "Проблема", "Ошибка", "не работает" | **Сценарий A** (исправление бага / исследование) — см. ниже |
| "Доработать", "Реализовать", "Новый функционал" | (в разработке) |
| "Почему", "Как работает", "Причина" | (в разработке) |

Агент сам определяет, какой сценарий применить, по ключевым словам в заголовке и описании задачи. Если ни один не подходит — читай общий принцип выше.

## Сценарий A: исправление бага / исследование проблемы

Применяй, когда задача содержит слова "проблема", "не работает", "исследовать", "ошибка" и т.п., или если в описании явно указан баг (например — некорректное поведение при определённых действиях).

### Шаг 1: Прочитать задачу

Сумму, описание, комментарии (особенно последние), чеклист, подзадачи, вложения. Для скриншотов — если агент может их видеть, проанализировать содержимое. Если нет — записать что есть в артефакте.

### Шаг 2: Определить продукты

Ищи упоминания продуктов:
- **Явные:** "Мобильное приложение", "Веб-админ панель", название продукта прямо в тексте
- **Неявные:** URL (домен, IP, порт), имена сервисов в запросах/описании (например `mifare_cgi` → продукт Домофоны)

Для каждого найденного продукта:
1. Найди slug в карте продуктов выше → получи repo_url
2. Если продукт не найден на карте — спроси пользователя: "Продукт X найден, но его репозиторий не записан. Где он лежит?"
3. Ответ пользователя запиши в `shared/jira-analysis/known_answers.json` (ключ = slug продукта, значение = `{repo_url, description}`)

### Шаг 3: Собрать артефакт

Сохрани в `shared/jira-analysis/<task-key>/analysis.json`:
```json
{
  "task_key": "ANDROIDSERVICE-XXXXX",
  "summary": "Краткое описание проблемы (1-2 предложения)",
  "type": "bug_fix",
  "products": [
    {"name": "AndroidService", "slug": "androidservice", "repo_url": "..."},
    {"name": "Мобильное приложение", "slug": "mobile-app", "repo_url": "..."}
  ],
  "requirements": ["Описание того, что нужно сделать для исправления"],
  "attachments_count": N,
  "next_action": "plan"
}
```

И `shared/jira-analysis/<task-key>/summary.md` — человекочитаемый отчёт:
- Что за задача (сводка + тип)
- Какие продукты затронуты (со ссылками на репозитории)
- Краткое описание проблемы из задачи
- Что уже сделано (если есть подзадачи Resolved/закрытые чеклисты)

### Шаг 4: Подготовить контекст для исполнителя

В summary.md добавь раздел "Контекст для кодера":
- Какие файлы/модули могут быть затронуты (если видно из описания задачи или комментариев)
- Ссылки на связанные проекты/репозитории, которые нужно клонировать
- Если есть URL запроса (как в ANDROIDSERVICE-33003: `http://10.160.12.23:8000/cgi-bin/mifare_cgi?...`) — это подсказка для поиска кода

### Пример из ANDROIDSERVICE-33003

Задача: "Исследовать проблему с синхронизацией с базой вк". В описании: порт 8000 → отредактирован на 80, но запрос ушёл на 8000. Продукты: AndroidService + Мобильное приложение (+ веб-админ панель). Подзадачи Resolved (окружение развёрнуто, анализ проведён), чеклист 0/9 TO DO.

Артефакт должен содержать:
- Продукты с репозиториями для клонирования
- URL `10.160.12.23:8000/cgi-bin/mifare_cgi?action=add...` как подсказку для поиска (git grep по mifare_cgi или портам)
- Ссылки на скриншоты вложения

## Когда обращаться к Confluence

Если задача касается архитектуры продукта, связей между сервисами или бизнес-логики — попробуй поискать информацию в Confluence (MCP-сервер "confluence"). Используй CQL по ключевым словам из задачи + названию проекта. Будь критичен: данные могут быть устаревшими. Не трять время на поиск, если задача — простой баг-фикс с ясным описанием.

## Формат артефакта анализа

`shared/jira-analysis/<task-key>/analysis.json`:
```json
{
  "task_key": "...",
  "summary": "...",
  "type": "bug_fix | feature | investigation",
  "products": [{"name": "...", "slug": "...", "repo_url": "..."}],
  "requirements": ["..."],
  "attachments_count": N,
  "next_action": "plan"
}
```

`shared/jira-analysis/<task-key>/summary.md`: краткое описание задачи для человека (или оркестратора).

## Запоминание ответов пользователя

Если агент не нашёл продукт на карте и спросил пользователя:
- Ответ записать в `shared/jira-analysis/known_answers.json` как ключ-значение.
- Ключ = slug продукта, значение = объект с repo_url + описанием.
- При следующем анализе — сначала читать known_answers.json; если ответ найден, использовать его без повторного вопроса.
