# Multiagents — обзор проекта

Мультиагентная чат-система на базе **pi coding agent SDK**: веб-интерфейс + сервер, где оркестратор маршрутизирует задачи специализированным агентам, а пользователь видит и контролирует всю цепочку в реальном времени. Работает полностью локально — модель запускается через OpenAI-совместимый API (llama.cpp / vLLM / LiteLLM), никаких облачных LLM не требуется.

---

## 1. Что это и зачем

Обычный чат с одной LLM знает только то, что вы ему рассказали, и всё делает «одними руками». Multiagents — это **команда агентов** в одном чате:

- **Оркестратор** принимает сообщение пользователя и решает, кто будет выполнять задачу;
- **Специализированные агенты** (кодовик, ревьюер, git-менеджер, веб-исследователь, планировщик фич и др.) делают свою часть работы в общей рабочей директории — **контексте задачи**;
- Агенты передают друг другу задачу через инструмент `route_to_agent` — возникает **цепочка**, которую пользователь видит в чате и может прервать или отменить на любом шаге.

Результат: одна команда «спланируй → напиши код → проверь → закоммить» выполняется разными агентами с разными промптами, инструментами и правилами, а пользователь остаётся в одной точке управления.

│   ├── code-worker/         #   Кодовый исполнитель

│   ├── git-manager/         #   Git-менеджер (ветки, коммиты, конфликты)

│   ├── registry.ts          #   Файловый регистр агентов

│   └── skill-registry.ts    #   Реестр глобальных навыков

**Ключевой принцип: всё — файлы.** Агенты, навыки, контексты, история — это обычные директории. Никакой базы данных: систему можно переносить, версионировать в git, инспектировать и чинить вручную.

## 3. Как это работает

### 3.1. Цикл сообщения

1. Пользователь отправляет сообщение (текст + опционально файлы) в выбранном контексте;
2. Сервер сохраняет вложения в `contexts/<id>/files/`, формирует из них markdown-ссылки и передаёт агенту;
3. **AgentRunner** берёт сообщение из очереди (глобальный мьютекс — один агент работает за раз, что соответствует одному локальному LLM-серверу) и запускает сессию pi текущего агента;
4. Агент работает: читает/пишет файлы, выполняет bash, вызывает MCP-инструменты, задаёт вопросы, маршрутизирует;
5. **Стриминг**: каждый токен события `message_update` уходит по WebSocket как `delta` — пузырь сообщения растёт в реальном времени (во время стрима рендерится plain-text, markdown применяется один раз по завершении хода — чат не «дрожит»);
6. Если агент вызвал `route_to_agent` — сервер планирует передачу и после завершения хода выполняет handoff;
7. История сохраняется в `messages.jsonl`, контекст переживает перезапуск сервера.

### 3.2. Handoff — передача задачи между агентами

```
Пользователь → Оркестратор ─route_to_agent→ code-worker ─route_to_agent→ code-reviewer
                        ↑                                                        │
                        └────────────── route_to_agent (отчёт) ←─────────────────┘
```

- Лимит 200 передач в одной цепочке — защита от циклов;
- Передача **ожидающая** (агент ещё работает, но уже «записал» маршрут) видна в UI и может быть **отменена** пользователем;
- Текущий агент можно **прервать** кнопкой ⏹;
- Опционально у каждого агента включается **«Забывать сессию после завершения шага»** — pi-сессия сбрасывается при передаче другому агенту, что даёт естественную сжатость контекста (история остаётся в `messages.jsonl`, LLM получает только текст).

### 3.3. ask_user — вопросы от агентов

Любой агент может вызвать `ask_user` → сервер ставит флаг ожидания → пользователь видит вопрос в чате → ответ уходит тому же агенту, цепочка не сбрасывается. Это исключает ложные срабатывания механизма восстановления.

### 3.4. Восстановление цепочки (recovery)

Локальные модели иногда завершают ход без tool call — «забыли» маршрутизировать. Если агент в цепочке завершил ход без `route_to_agent` и без `ask_user`, сервер автоматически запускает оркестратора с промптом «цепочка прервалась — проверь состояние». Оркестратор решает: завершить задачу, передать дальше или спросить пользователя. Максимум 2 восстановления на цепочку.

### 3.5. Watchdog

Если агент завис (модель не отвечает), watchdog принудительно завершает сессию и сообщает об ошибке — мьютекс не блокируется навсегда.

## 4. Концепции системы

### 4.1. Агенты как директории

```
agents/<id>/
├── AGENT.md       # Системный промпт
├── config.json    # { name, tools[], model?, forgetSessionAfterStep? }
├── rules/         # (опц.) правила — markdown-файлы, инжектятся в промпт
└── skills/        # (опц.) личные навыки агента
```

Новый агент = новая директория. `agent-creator` делает это в рантайме через инструменты `create_agent` / `delete_agent`, UI обновляется мгновенно. У агента можно выбрать: набор инструментов, отдельную модель, сброс сессии после шага.

### 4.2. Контексты задач

Каждый чат — **контекст**: директория на диске, где работают все агенты цепочки. Пользователь создаёт/переименовывает/удаляет контексты в сайдбаре; они группируются по дате создания и показывают свой размер (Б/КБ/МБ/ГБ). Контекст можно **скачать архивом** (zip всей директории) одной кнопкой.

### 4.3. Файлы и изображения

- Пользователь прикрепляет файлы: изображения уходят модели как мультимодальный ввод, любые файлы — как ссылки на скачивание;
- **Агенты умеют присылать изображения**: скриншоты и картинки из результатов инструментов (например, Chrome через MCP) автоматически сохраняются в контекст и показываются в чате миниатюрой; клик — Lightbox с просмотром на весь экран и кнопкой скачивания;
- Ссылки на файлы в ответах агентов маскируются в рабочие URL (`/api/files?ctx=…&path=…`) — модель может писать пути как угодно, UI всё равно откроет файл. **Санитайзер** сверяет каждую ссылку с диском: выдуманной моделью ссылки не доходят до пользователя.

### 4.4. Навыки (skills)

Глобальные навыки (`skills/<id>/SKILL.md` + `config.json`) и личные (в директории агента). Пользователь **подключает навык к чату в любой момент** — с этого момента он передаётся агентам вместе с сообщениями. Навык — это «рецепт»: тело markdown-инструкции, которое точечно меняет поведение агентов без правки их промптов.

### 4.5. MCP — внешний инструментарий

Агенты получают доступ к MCP-серверам (например, `chrome-devtools` для реальной работы в браузере): инструменты регистрируются через адаптер `pi-mcp-adapter`, плюс есть гейтвей-инструмент `mcp` (поиск/вызов любого MCP-инструмента) и `mcpScript` (JS-скрипты с циклами по нескольким MCP-вызовам). Новые агенты получают `mcp`/`mcpScript` в инструментах по умолчанию.

### 4.6. Модели

Глобальная модель задаётся в `config.json`; у отдельного агента можно задать свою (`model` в `config.json`). Поддерживается несколько LLM-провайдеров одновременно (в конфиге: локальный llama.cpp, домашний/рабочий серверы, корпоративный LiteLLM) — переключение без перезапуска.

## 5. Веб-интерфейс

- **Сайдбар**: контексты по датам (с размером и временем создания), список агентов;
- **Чат**: стриминг в реальном времени, markdown (GFM + подсветка кода), цепочка handoff'ов видна как отдельные сообщения, ожидающая передача — панелью с кнопкой отмены, вопросы агентов — выделенными блоками;
- **Управление**: остановка агента, отмена передачи, усечение истории («удалить историю начиная с этого сообщения»), скачивание архива контекста;
- **Файлы**: миниатюры, Lightbox, drag-and-drop и вставка из буфера;
- **Редактор агентов** прямо в UI: промпт, инструменты чекбоксами (с подсказками), модель, сброс сессии;
- **Мобильная адаптация**: drawer-сайдбар, адаптивные пузыри, smart auto-scroll (не догоняет стрим, если пользователь скроллит вверх).

## 6. Сильные стороны и уникальные фичи

### Уникальность архитектуры

1. **Полностью файловая система** — без БД: агенты, навыки, контексты, история — директории и jsonl. Прозрачно, переносимо, отлаживается редактором;
2. **Оркестрация через tool call, а не код** — маршрутизацию решает LLM (`route_to_agent`), цепочка строится динамически под задачу, а не по жёсткому workflow;
3. **Глобальный мьютекс + очередь** — честная сериализация под один локальный LLM: нет гонок за модель, сообщения не теряются;
4. **Recovery-оркестратор** — самоисцеление цепочки: прерванный из-за «забывчивости» модели ход автоматически проверяется оркестратором, максимум 2 раза;
5. **Пользователь в контуре на каждом шаге** — отмена ожидающей передачи, остановка агента, вопросы `ask_user`, усечение истории: полная контролируемость автономной цепочки.

### Управление агентами

6. **Агент-создатель** — команда расширяется в рантайме из чата («создай агента X»), UI обновляется мгновенно;
7. **Per-agent настройки**: свой промпт, правила (`rules/`), навыки (`skills/`), набор инструментов, отдельная модель, сброс сессии после шага (естественное сжатие контекста при передаче);
8. **Навыки по подключению к чату** — точечное изменение поведения без правки промптов, в любой момент беседы.

### Прозрачность и надёжность работы

9. **Видимая цепочка**: каждый handoff — отдельное сообщение с указанием «откуда → куда» и причиной;
10. **Изображения из инструментов в чат** — скриншоты браузера от web-агента показываются миниатюрой, по клику — на весь экран со скачиванием;
11. **Санитайзер ссылок** — модель может выдумывать пути и URL, но ссылка дойдёт до UI только если файл реально существует в контексте (проверка по диску);
12. **Watchdog** — зависший агент принудительно завершается, мьютекс не блокируется;
13. **Восстановление после перезапуска** — история в `messages.jsonl`, состояние цепочки в `context.json`: сервер можно перезапустить, контекст продолжит жить.

### Эксплуатация

14. **Локальность**: модель — OpenAI-совместимый API (llama.cpp / vLLM / LiteLLM), данные не покидают машину; несколько провайдеров на выбор, включая удалённые домашние/рабочие серверы;
15. **Архивация контекста одной кнопкой** — zip всей директории задачи (код, отчёты, история) для переноса и хранения;
16. **Мобильный UI** — полный функционал с телефона.

## 7. Технологии

| Слой | Стек |
|------|------|
| Ядро агентов | `@earendil-works/pi-coding-agent` (pi SDK): сессии, инструменты, MCP |

## 8. Запуск

```bash
# Требования: Node.js 20+, LLM-сервер с OpenAI-совместимым API
npm install
npm run dev            # разработка: Vite HMR :5173 (прокси на :3000)
npm run build -w web && npm run start -w server   # продакшен: http://localhost:3000
```

Минимальный конфиг (`config.json`):

```json
{
  "model": "<provider>/<model>",
  "port": 3000,
  "providers": { "<provider>": { "url": "http://…", "apiKey": "…" } }
}
```

## 9. Типовой сценарий работы

Пользователь пишет в новом контексте: *«Сделай API управления задачами: спланируй, напиши код с тестами, проверь и закоммить»*.

1. **Оркестратор** читает задачу → `route_to_agent(feature-planner)`;
2. **feature-planner** декомпозирует фичу по своим правилам (атомарные задачи, реалистичные оценки) → пишет план в контекст → передаёт дальше;
3. **code-worker** реализует код и тесты в рабочей директории контекста;
4. **code-reviewer** проходит ревью по своим правилам, возвращает замечания либо передаёт результат;
5. **git-manager** делает коммит/ветку по правилам git-flow;
6. Результат возвращается **оркестратору**, который суммирует отчёт для пользователя.

На каждом шаге пользователь видит цепочку в чате, может задать вопрос любому агенту (те же `ask_user`), прервать агента или отменить передачу. По итогу — один zip-архив со всем: планом, кодом, тестами, ревью и историей диалога.
