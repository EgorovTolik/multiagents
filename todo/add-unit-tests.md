# Добавить unit-тесты для критической логики

**Статус:** запланировано  
**Приоритет:** высокий  
**Сложность:** средняя  
**Зависимости:** желательно после рефакторинга runner.ts (todo/refactor-runner.md)

## Обоснование

В проекте нет тестовой инфраструктуры — только ручной QA через UI. Для системы с такой сложной логикой handoff, восстановления цепочки и глобального мьютекса это критично: регрессии обнаруживаются только в продакшене.

## Детальное описание работ

### 1. Настроить тестовую инфраструктуру
- Выбрать фреймворк: Vitest или Jest (рекомендация: Vitest — быстрый, нативная поддержка ESM)
- Добавить зависимости в `package.json` (devDependencies)
- Создать `vite.config.ts` или `jest.config.ts`
- Настроить окружение для тестов (mock файловых операций)

### 2. Тесты для MutexManager
**Файл:** `tests/mutex.test.ts`

Сценарии:
- Агент получает мьютекс, когда свободен
- Агент блокируется, когда занят в другом контексте
- FIFO-очередь: второй запроситель ждёт освобождения первого
- Release передаёт мьютекс следующему в очереди
- Race conditions: параллельные acquire от разных агентов

### 3. Тесты для QueueManager
**Файл:** `tests/queue.test.ts`

Сценарии:
- Сообщения добавляются в очередь, когда агент занят
- `dispatchQueue()` выбирает первое сообщение из свободного контекста
- После завершения хода запускается следующее сообщение
- Очередь других контекстов не блокирует текущий

### 4. Тесты для RecoveryEngine
**Файл:** `tests/recovery.test.ts`

Сценарии:
- Обрыв цепочки → вызов chain-router (recoveryMode="router_agent")
- Обрыв цепочки → вызов orchestrator (recoveryMode="orchestrator_check")
- Обнаружение незавершённой задачи (нет result-файла) → возврат агенту
- Chain-router не принял решение → fallback на оркестратор
- Достигнут лимит recoveries → сообщение пользователю, остановка

### 5. Тесты для ProviderRegistry
**Файл:** `tests/providers.test.ts`

Сценарии:
- Регистрация провайдера с моделями из live API
- Fallback на модели из config.json при недоступности сервера
- Обнаружение недоступной модели агента → сброс или выбор единственной доступной
- До-регистрация новой модели после изменения конфига

### 6. Тесты для ContextStore
**Файл:** `tests/context-store.test.ts`

Сценарии:
- Создание/удаление контекста
- Сохранение и чтение сообщений (JSONL)
- Применение навыков к контексту
- Архивирование контекста в ZIP
- Маскирование путей файлов в сообщениях

### 7. Интеграционные тесты (опционально, после unit)
**Файл:** `tests/integration/handoff.test.ts`

Сценарии:
- Полный цикл: user → orchestrator → code-worker → code-reviewer → orchestrator
- Обрыв цепочки и восстановление
- Параллельные цепочки в разных контекстах

## Критерии готовности

- [ ] Тестовая инфраструктура настроена, тесты запускаются через `npm test`
- [ ] Написаны тесты для MutexManager (≥5 сценариев)
- [ ] Написаны тесты для QueueManager (≥3 сценария)
- [ ] Написаны тесты для RecoveryEngine (≥6 сценариев)
- [ ] Написаны тесты для ProviderRegistry (≥4 сценария)
- [ ] Все тесты проходят (`npm test` — зелёный)
- [ ] CI/CD интеграция (запуск тестов при push/pull request)

## Рекомендации по mocking

- Файловые операции: mock `fs` через Vitest/Jest или использовать временные директории
- Pi SDK сессии: mock `createAgentSession`, `session.prompt()`
- WebSocket broadcast: mock callback `emit`
- Сеть (fetch): mock через Vitest `vi.fn()` или nock
