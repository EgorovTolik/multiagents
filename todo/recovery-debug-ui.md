# UI для отладки восстановления цепочки (recovery)

**Статус:** запланировано  
**Приоритет:** низкий/средний  
**Сложность:** средняя  
**Зависимости:** желательно после улучшения типизации (todo/improve-typing.md)

## Обоснование

Когда система автоматически восстанавливает обрывы цепочки, пользователь видит только результат — сообщение от другого агента. Ему не понятно, что именно произошло: был ли обрыв, какое решение принял chain-router, сколько раз сработало восстановление. Это затрудняет отладку и доверие к системе.

## Детальное описание работ

### 1. Визуализировать события recovery в чате
Добавить системные сообщения при каждом событии восстановления:

**При обнаружении обрыва:**
```
⚠️ ЦЕПОЧКА ПРЕРВАЛАСЬ
Агент «code-worker» завершил ход без маршрутизации.
Запускаю восстановление...
```

**При вызове chain-router:**
```
🔀 Запрос к цепочке агентов: chain-router должен принять решение о продолжении работы.
```

**При принятии решения:**
```
✅ Решение принято: передача на «code-reviewer»
Причина: код готов, требуется ревью перед коммитом
```

**При fallback на оркестратора:**
```
⚠️ Chain-router не смог принять решение. Передаю оркестратору.
```

**При достижении лимита recoveries:**
```
🔄 Восстановление #3 из 40 выполнено успешно.
```

### 2. Добавить счётчик восстановлений в UI
Показать пользователю, сколько раз сработало восстановление для текущей цепочки:

**Компонент:** `web/src/components/RecoveryBadge.tsx` (новый)

```tsx
interface RecoveryBadgeProps {
  recoveryCount: number;
  maxRecoveries: number;
}

export function RecoveryBadge({ recoveryCount, maxRecoveries }: RecoveryBadgeProps) {
  if (recoveryCount === 0) return null;
  
  const isWarning = recoveryCount > maxRecoveries * 0.5;
  
  return (
    <span className={`badge ${isWarning ? "warning" : "info"}`}>
      🔄 Восстановления: {recoveryCount}/{maxRecoveries}
    </span>
  );
}
```

Разместить в заголовке чата или рядом с текущим агентом.

### 3. Логи восстановления в контексте
Добавить поле `recoveryLog` в `ContextMeta`:
```typescript
interface RecoveryEntry {
  timestamp: number;
  brokenAgent: string;
  routerDecision: string;
  result: "success" | "fallback" | "limit_reached";
}

interface ContextMeta {
  // ... существующие поля
  recoveryLog?: RecoveryEntry[];
}
```

Записывать каждое событие восстановления и отправлять в UI.

### 4. История восстановлений на странице контекста
Добавить секцию "История восстановления" на страницу деталей контекста:

**Компонент:** `web/src/components/RecoveryHistory.tsx` (новый)

Отображать таблицу:
| Время | Агент | Решение | Результат |
|-------|-------|---------|-----------|
| 14:30 | code-worker | Передача на reviewer | ✅ Успешно |

### 5. WS-события для recovery
Добавить новые типы WS-сообщений:

```typescript
// Server → Client
{ type: "recovery_started"; ctxId: string; brokenAgent: string }
{ type: "recovery_decision"; ctxId: string; decision: string; targetAgent: string }
{ type: "recovery_completed"; ctxId: string; success: boolean; count: number }
```

Отправлять из runner.ts при каждом событии восстановления.

### 6. Настройка лимита recoveries в UI
Добавить поле ввода `maxRecoveries` на страницу настроек (`SettingsPage.tsx`). Позволить пользователю настроить лимит без редактирования config.json вручную.

## Критерии готовности

- [ ] Пользователь видит системные сообщения при событиях восстановления
- [ ] Счётчик восстановлений отображается в UI чата
- [ ] WS-события для recovery отправляются сервером
- [ ] История восстановлений доступна на странице контекста
- [ ] Лимит recoveries можно настроить через UI

## Риски

- Излишняя детализация может раздражать пользователя (спам системными сообщениями)
- Увеличение трафика WS-событий (не критично для такого размера проекта)
