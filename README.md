# Multiagents

Мультиагентная чат-система на базе [pi coding agent SDK](https://github.com/earendil-works/pi-coding-agent). Веб-интерфейс + сервер, где оркестратор маршрутизирует задачи специализированным агентам, а пользователь видит и контролирует всю цепочку.

## Возможности

- **Оркестратор** — принимает сообщение пользователя, маршрутизирует его специализированному агенту через `route_to_agent`
- **Цепочка передач** — агент может передать задачу другому агенту; пользователь видит всю цепочку в UI и может прервать передачу
- **Регистр агентов** — файловая система: каждый агент = подкаталог с `AGENT.md` (системный промпт) и `config.json` (название, инструменты)
- **Агент-создатель** — создаёт, редактирует и удаляет агентов в рантайме; UI обновляется мгновенно
- **Контексты задач** — директории на диске, где все агенты в цепочке работают; пользователь переключается между контекстами
- **Глобальный мьютекс** — один агент работает за раз (один локальный LLM-сервер)
- **Восстановление цепочки** — если агент завершил ход без маршрутизации, оркестратор автоматически проверяет состояние
- **ask_user** — любой агент может задать вопрос пользователю и ждать ответа без срабатывания восстановления
- **Веб-исследование** — агент web-researcher работает через Chrome (MCP chrome-devtools)
- **Загрузка файлов** — изображения (мультимодальный ввод) и любые файлы (скачивание по ссылке)
- **Lightbox** — клик по изображению открывает просмотр на весь экран с кнопкой скачивания
- **Markdown** — рендеринг ответов (GFM, подсветка кода)
- **Мобильный UI** — drawer-сайдбар, адаптивные пузыри, smart auto-scroll

### Ключевые компоненты

| Файл | Роль |
|------|------|
| `server/src/runner.ts` | AgentRunner: глобальный мьютекс, handoff, watchdog, recovery, кастомные инструменты |
| `server/src/registry.ts` | AgentRegistry: файловый регистр агентов (AGENT.md + config.json) |
| `server/src/context-store.ts` | ContextStore: контексты как директории, maskPaths, messages.jsonl |
| `server/src/index.ts` | Express + WebSocket: API, WS-протокол, статика |
| `web/src/App.tsx` | Весь UI: sidebar, чат, стрим, lightbox, файлы, мобильный drawer |
| `web/src/api.ts` | WebSocket-клиент, типы сообщений |

## Как это работает

### Цикл сообщения

1. **Пользователь** отправляет сообщение (текст + опционально файлы)
2. **Сервер** сохраняет файлы в `contexts/<id>/files/`, копирует в `previews/`, формирует markdown-ссылки
3. **AgentRunner** берёт сообщение из очереди (глобальный мьютекс), запускает сессию текущего агента
4. **Агент** работает: использует инструменты (bash, read, write, MCP, ask_user, route_to_agent)
5. **Стриминг**: события `message_update` → WS `delta` → UI обновляет пузырь в реальном времени
6. **Handoff**: `route_to_agent` планирует передачу (`pendingHandoff`); после завершения хода `run()` выполняет `doHandoff()`
7. **Восстановление**: если агент завершил ход без `route_to_agent` и без `ask_user` — оркестратор получает автопроверку (до 2 раз)

### Handoff (передача задачи)

```
Пользователь → Оркестратор → route_to_agent(code-worker)
                                ↓
                          code-worker работает
                                ↓
                    route_to_agent(code-reviewer)
                                ↓
                          code-reviewer работает
                                ↓
                    route_to_agent(orchestrator)  ← отчёт
                                ↓
                          Оркестратор → Пользователь
```

- Лимит: 200 передач в одной цепочке
- Пользователь может **отменить** ожидающую передачу (кнопка в UI)
- Пользователь может **прервать** текущий агент (кнопка ⏹)

### ask_user

Агент вызывает `ask_user` → сервер ставит флаг `awaitingUser` → агент завершает ход → пользователь видит вопрос → ответ уходит тому же агенту (цепочка не сбрасывается).

### Восстановление цепочки

Если агент «в цепочке» (запущен handoff'ом) завершил ход без `route_to_agent`:
1. Сервер запускает оркестратора с промптом «Цепочка прервалась — проверь»
2. Оркестратор решает: завершить задачу / передать дальше / спросить пользователя
3. Максимум 2 восстановления на цепочку

## WS-протокол

### Client → Server

| Тип | Поля | Описание |
|-----|------|----------|
| `message` | `ctxId`, `text`, `files?` | Сообщение пользователя |
| `create_context` | — | Создать контекст |
| `delete_context` | `ctxId` | Удалить контекст |
| `load_context` | `ctxId` | Загрузить контекст |
| `abort` | `ctxId` | Прервать текущего агента |
| `cancel_handoff` | `ctxId` | Отменить ожидающую передачу |
| `list_contexts` | — | Список контекстов |
| `rename_context` | `ctxId`, `name` | Переименовать контекст |

### Server → Client

| Тип | Поля | Описание |
|-----|------|----------|
| `agents` | `agents[]` | Список агентов |
| `contexts` | `contexts[]` | Список контекстов |
| `context_created` | `ctxId`, `name` | Контекст создан |
| `context_deleted` | `ctxId` | Контекст удалён |
| `context_loaded` | `ctxId`, `messages[]` | Контекст загружен |
| `context_renamed` | `ctxId`, `name` | Контект переименован |
| `message` | `ctxId`, `message` | Новое сообщение |
| `delta` | `ctxId`, `agentId`, `text` | Стриминг (приращение) |
| `assistant_end` | `ctxId`, `agentId` | Конец хода агента |
| `run_start` | `ctxId`, `agentId` | Агент начал работу |
| `run_end` | `ctxId`, `agentId` | Агент завершил работу |
| `run_state` | `active` | Состояние мьютекса (при подключении) |
| `handoff` | `ctxId`, `from`, `to`, `reason` | Передача состоялась |
| `handoff_pending` | `ctxId`, `to`, `reason` | Передача ожидает |
| `handoff_cancelled` | `ctxId` | Передача отменена |
| `ask_user` | `ctxId`, `agentId`, `question` | Агент задаёт вопрос |
| `message_received` | `ctxId` | Подтверждение получения |
| `error` | `ctxId`, `message` | Ошибка |

## Кастомные инструменты

| Инструмент | Доступен | Описание |
|------------|----------|----------|
| `route_to_agent` | Все (кроме agent-creator) | Маршрутизация задачи другому агенту |
| `ask_user` | Все | Задать вопрос пользователю, ждать ответа |
| `create_agent` | agent-creator | Создать нового агента |
| `delete_agent` | agent-creator | Удалить агента (защита: orchestrator, agent-creator) |

## Конфигурация

### `config.json` (корень)

```json
{
  "model": "eac-mac-ai/Qwen3.6-27B-Q4_K_M.gguf",
  "port": 3000
}
```

- `model` — идентификатор модели (провайдер/модель), определяется в `~/.pi/agent/models.json`
- `port` — порт HTTP + WebSocket

### `agents/<id>/config.json`

```json
{
  "name": "Кодовый исполнитель",
  "tools": ["read", "write", "bash", "route_to_agent", "ask_user"]
}
```

- `name` — отображаемое имя (на русском)
- `tools` — явный список разрешённых инструментов (кастомные должны быть в списке)

### `agents/<id>/AGENT.md`

Системный промпт агента. Глобальные файлы из `system/*.md` добавляются автоматически (алфавитный порядок).

## Запуск

### Требования

- Node.js 20+
- LLM-сервер (например, llama.cpp с OpenAI-совместимым API)
- Конфигурация модели в `~/.pi/agent/models.json`

### Установка

```bash
npm install
```

### Разработка

```bash
npm run dev
# Сервер: http://localhost:3000 (WS + HTTP)
# Vite HMR: http://localhost:5173 (прокси на 3000)
```

### Продакшен

```bash
npm run build -w web   # Собрать фронтенд в web/dist
npm run start -w server # Запустить сервер (сервит web/dist)
# http://localhost:3000
```

## Технологии

- **Ядро**: `@earendil-works/pi-coding-agent` (pi SDK) — сессии агентов, инструменты, MCP
- **Сервер**: Express 4, WebSocket (ws), TypeScript, tsx (ESM)
- **Фронтенд**: React 18, Vite 6, Tailwind CSS 4, react-markdown + remark-gfm + rehype-highlight
- **Модель**: локальный LLM через OpenAI-совместимый API (llama.cpp / vLLM)
- **MCP**: chrome-devtools (веб-исследование)

## Известные особенности локальной модели

Локальные модели (Qwen 27B) имеют ограничения:
- Иногда завершают ход без tool call (решается recovery)
- Игнорируют инструкции «не делай сам, маршрутизируй» (решается строгими промптами)
- Не всегда используют `ask_user` (решается явными правилами в AGENT.md)
- Пишут стихи вместо кратких имён (решается примерами в промпте)
