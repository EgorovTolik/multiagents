# Декомпозиция задач

## Подход к декомпозиции

### Принцип WBS (Work Breakdown Structure)
1. Начни с конечного результата
2. Разбей на крупные компоненты/модули
3. Каждый компонент разбей на логические шаги
4. Каждый шаг — атома́рная задача

### Типовые категории этапов

| Категория | Когда применять | Примеры |
|-----------|----------------|---------|
| Анализ | Начало любой фичи | Изучение требований, анализ влияния, исследование API |
| Дизайн | Когда нужно архитектурное решение | Проектирование БД, выбор паттернов, определение интерфейсов |
| Реализация | Когда план готов | Создание компонентов, написание логики, интеграция |
| Тестирование | После реализации | Unit-тесты, интеграционные тесты, E2E тесты |
| Ревью | После тестирования | Code review, рефакторинг |
| Документация | Параллельно или после | Обновление docs, changelog, комментарии в коде |
| Деплой | В конце | Подготовка к релизу, мониторинг |

### Критерии хорошего этапа

✅ **INVEST для задач:**
- **I**ndependent — частично независимый
- **N**egotiable — детали можно обсудить
- **V**aluable — несёт ценность
- **E**stimable — можно оценить
- **S**mall — выполним за 1-2 дня
- **T**estable — есть критерии готовности

❌ **Плохие признаки:**
- Этап на 2+ недели
- 'Изучить технологию' без конкретного вывода
- Нет критериев готовности
- Зависит от 5+ других этапов

### Методики декомпозиции

1. **По слоям архитектуры:** frontend → backend → database → infra
2. **По пользовательским сценариям:** happy path → edge cases → error handling
3. **По временным спринтам:** MVP → v1.0 → polish
4. **По компонентам:** каждый UI-компонент или модуль отдельно

### Совет
Если фича большая (> 20 этапов) — предложи разбить на несколько фич или спринтов.
