# Работа с вложенными Git-репозиториями

Применяй автоматически, когда проект или папка, с которой нужно работать, находится **внутри другого Git-репозитория** — типично для проектов в папках `projects/`, `contexts/`, `workspaces/` внутри родительского репо (например, `multiagents`).

## 1. Проверка контекста — ОБЯЗАТЕЛЬНО перед любой командой

```bash
git rev-parse --show-toplevel   # корень ТЕКУЩЕГО репозитория (не .../multiagents?)
ls -la <путь_к_проекту>         # есть тут .git? какие файлы проекта?
if [ -d "<проект>/.git" ]; then echo "это репо"; else echo "не репо — инициализировать"; fi
```

`rev-parse --show-toplevel` из папки без `.git`, но внутри ignored-папки, **поднимется до ближайшего .git вверх** — может неожиданно выдать корень родительского репо. Всегда сверяй с `ls -la`.

## 2. Ключевые принципы (почему агент ошибается)

- **Вложенный `.git` = отдельный контекст.** Git использует его как корень для всех команд из этой папки и ниже.
- **`.gitignore` отключает отслеживание В ОБЕ СТОРОНЫ.** Если папка в `.gitignore` внешнего репо:
  - внешний репо не видит файлы внутри, `git add .` их не берёт, в коммиты не попадают;
  - внутренние проекты НЕ знают о внешнем репо.
- **Старт из ignored-папки без `.git` → `fatal: not a git repository`** (или неожиданно внешний репо). Убедись, что путь содержит `.git`, либо инициализируй своё репо.

## 3. Сценарий ошибки — НЕ ПОВТОРЯТЬ (самый частый баг)

```bash
# Агент внутри project-a хочет обновить ВНЕШНИЙ репо:
cd /path/to/outer-repo/projects/project-a
git add . && git commit -m "Update outer repo"
# ❌ Результат: компит попал в project-a, а не во внешний репо!
```

Как правильно — всегда явно указывать целевой репозиторий через `-C`:

```bash
INNER_PROJECT="/path/to/outer-repo/projects/project-a"
git -C "$INNER_PROJECT" add .
git -C "$INNER_PROJECT" commit -m "..."

# Если нужно работать с ВНЕШНИМ репо, находясь внутри вложенного:
OUTER_ROOT="/path/to/outer-repo"
git -C "$OUTER_ROOT" status
git -C "$OUTER_ROOT" add .
git -C "$OUTER_ROOT" commit -m "Update outer repo"
```

## 4. Явное указание репозитория — через `-C`, никогда не надейся на `cd`

**Плохо:**
```bash
cd /path/to/workspace/projects/my-feature
git add .   # какой репо? зависит от контекста!
```

**Хорошо:**
```bash
MY_FEATURE="/path/to/workspace/projects/my-feature"
git -C "$MY_FEATURE" add .
git -C "$MY_FEATURE" commit -m "feat: ..."
```

## 5. Альтернатива: Submodules vs `.gitignore`

- **`.gitignore`** — внутренние проекты НЕ отслеживаются внешним репо, при клонировании теряются. Подходит, когда проект должен быть изолированным (как раз случай multiagents/contexts).
- **Submodules** — проекты хранят коммит и URL в внешнем репо, требуют `git clone --recursive`. Сложнее синхронизация, но структура переносится целой.

```bash
# Во внешнем репо:
git submodule add /path/to/project-a projects/project-a
git commit -m "Add project-a as submodule"
```

## 6. Чеклист-резюме (прогони перед действием)

1. Всегда явно указывай целевой репозиторий через `git -C <path>` или точный `cd` с проверкой.
2. Проверяй наличие `.git` перед командами, особенно в `projects/`, `workspaces/`, `contexts/`.
3. Определяй текущий репо через `git rev-parse --show-toplevel`.
4. Не предполагай, что родительская папка — нужный репо.
5. При нескольких репо одновременно — отдельная переменная пути для каждого.

## 7. Связь с другими навыками

- Проект уже репо → работай как есть (`commit-and-push`, `merge-operations`).
- Проекта нет как репо, но дан URL пустого remote + поручение «залей сам» → `initialize-repo-and-push` (инициализируй через `git -C <проект> init`, пуш на master).
